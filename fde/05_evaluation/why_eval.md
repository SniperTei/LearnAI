# 为什么评估是 FDE 的核心能力

> 没有 demo 的工程师拿不到面试，**没有评估的工程师拿不到客户**。

---

## 一个真实场景

你给客户演示了 RAG 系统，客户问："它答得准吗？"

| 你的回答 | 客户的反应 |
|---------|-----------|
| "我感觉挺准的" | 😐 |
| "我们测过几十条，大部分都对" | 🤔 |
| "RAGAS faithfulness 0.87，对比上个月提升 12%，错答的 case 主要集中在 X 类，下一步我们打算…" | 🤩 |

**差距不在技术，在评估**。

---

## 为什么 AI 项目比传统软件更需要评估

### 传统软件：确定性
```
输入 → 代码 → 输出（可预测、可重现）
```
测试方法：单元测试 / 集成测试。**100% 覆盖就能保证质量**。

### LLM 应用：概率性
```
输入 → 模型 → 输出（每次可能不一样、对错模糊）
```
测试挑战：
- 同一输入，输出可能不同
- "对"和"错"经常不是 0/1，是连续光谱
- 模型升级后，原本好的 case 可能变差
- 用户问法千变万化，无法穷举

**结论**：传统测试方法对 LLM 应用**部分失效**，必须引入新的评估体系。

---

## 没有评估，你会怎样（4 种死法）

### 死法 1：上线即崩
你的 demo 在客户现场演示完美。上线后用户问的问题千奇百怪，系统 30% 答错。
**根因**：你没测过 demo 数据集之外的 case。

### 死法 2：改了 prompt 不知道是变好还是变差
你调了一版 prompt，看起来"答得更流畅了"，但实际 faithfulness 下降。
**根因**：没有 baseline，全凭感觉。

### 死法 3：模型升级翻车
OpenAI 出了新版 GPT，你升级了，发现老客户的核心 case 全坏了。
**根因**：没有"黄金集"保护关键场景。

### 死法 4：成本失控
你不知道哪些请求浪费钱，哪些是真有用的。
**根因**：没有评估"性价比"的维度。

---

## FDE 视角的评估三目标

### 目标 1：**信心（Confidence）**
- 你能不能用数据说"这个系统达到了 X 水平"
- 客户/老板问"敢上线吗"，你有答案

### 目标 2：**对比（Comparison）**
- v1 vs v2，谁更好？好多少？
- 用 GPT-4o vs 用 Claude，值不值差价？
- 加 reranking，提升多大？

### 目标 3：**指引（Guidance）**
- 评估不只是打分，是告诉你**下一步该改哪里**
- 错的 case 集中在哪类问题上？
- 是召回不够、还是生成跑偏？

---

## 评估的 3 个层次（必背）

```
         ┌──────────────────────────────┐
         │   在线评估（Online）          │  真实用户、真实环境
         │   - 用户反馈、采纳率          │
         │   - A/B 测试                  │
         └──────────────────────────────┘
                     ↓ 反哺
         ┌──────────────────────────────┐
         │   离线评估（Offline）         │  上线前必做
         │   - Golden set + 指标        │
         │   - RAGAS / LLM-as-Judge     │
         └──────────────────────────────┘
                     ↓ 校准
         ┌──────────────────────────────┐
         │   人在环（Human-in-loop）    │  真理基准
         │   - 专家标注                  │
         │   - 用户深度访谈              │
         └──────────────────────────────┘
```

- **离线**：上线前用静态数据集测，便宜、快
- **在线**：上线后看真实用户行为，真实但慢、有风险
- **人在环**：用人工标注校准上面两个，准但贵

**完整的评估体系 = 三者结合**，不是只做一种。

---

## 评估的两个时间点

### 1. 上线前（Offline Eval）
回答："**敢不敢上线**？"
- 用 Golden Set 跑指标
- 跨版本对比
- 检查回归（regression）

### 2. 上线后（Online Eval）
回答："**真的好用吗**？"
- 真实用户反馈
- 行为指标（采纳率、留存）
- A/B 测试新功能

**两个都不可少**。离线好 ≠ 在线好，反之亦然。

---

## 评估的常见误区

❌ **"我用了 LangChain 自带的 evaluator"**——它只测了你流程没报错，没测回答质量
❌ **"我们跑了 1000 条测试"**——但如果都是简单 case，等于没测
❌ **"LLM-as-Judge 一切"**——LLM 评委自己也有偏差
❌ **"等业务给我 KPI"**——业务给不了，FDE 要自己造指标
❌ **"评估一次就够了"**——模型、prompt、数据变了都要重评

---

## 一个反直觉的结论

> **大部分 AI 项目失败的根因不是模型不行，是没人认真做评估。**

- 你以为模型不行，其实是 prompt 没调好（没评估不知道）
- 你以为系统很准，其实只在你测的 10 条上准（没 golden set 不知道）
- 你以为用户喜欢，其实只是没用脚投票（没在线指标不知道）

**评估能力 = 把"凭感觉"变成"凭数据"的能力**。这是 FDE 区别于 demo 工程师的核心。
