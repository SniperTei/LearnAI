# 在线用户反馈采集

> 离线评估告诉你"系统能用"，在线反馈告诉你"用户真的喜欢"。

---

## 离线 vs 在线：根本区别

| 维度 | 离线评估 | 在线反馈 |
|------|---------|---------|
| 数据 | Golden set（你造的） | 真实用户问的 |
| 评估者 | LLM judge / 标注员 | 用户（用脚投票） |
| 时间 | 上线前 | 上线后 |
| 偏差 | 你猜的"典型问题" | 真实的"长尾问题" |
| 信号强度 | 强（结构化） | 弱（需要设计采集） |

**核心洞察**：离线评估永远猜不到用户会问什么。
真实 query 的分布和你想的差 10 倍。

## 用户反馈的两种类型

### 显式反馈（Explicit）
用户**主动**告诉你好不好。

| 形式 | 优点 | 缺点 |
|------|------|------|
| 👍 / 👎 | 简单，采集率高 | 信号粗糙 |
| 1–5 星评分 | 有粒度 | 用户嫌烦 |
| 文本评论 | 信号丰富 | 采集率极低 |
| 修正文本（user edited answer） | 强信号 | 实现复杂 |
| 举报（"答错了"） | 强负信号 | 偏消极 |

**FDE 推荐组合**：**👍👎（基础） + 修正文本（关键） + 举报（兜底）**

### 隐式反馈（Implicit）
从用户行为推断。

| 信号 | 含义 |
|------|------|
| 复制了答案 | 有用 |
| 重新问了一遍（改写） | 不满意 |
| 转人工 / 切到搜索 | 失败 |
| 停留时长 | 长不一定好，短可能跑题 |
| 分享 / 收藏 | 高度有用 |
| 关闭页面 | 失败 |

**隐式信号更真实**（用户不会撒谎），但解读难。

## 反馈采集 UI 的 5 个设计原则

### 1. **降低摩擦**
- 不要弹窗、不要问卷
- 👍👎 直接在答案旁
- 一键提交

```
┌─────────────────────────────┐
│ AI: 入职享 15 天年假。       │
│                             │
│ 👍  👎   📋 复制  ⚠️ 举报   │
└─────────────────────────────┘
```

### 2. **及时**
答案出现后立刻可以反馈，不要等对话结束。

### 3. **可选**
不强制反馈——强制会让用户随便点。

### 4. **追问"为什么"（但不强制）**
点 👎 后展开一个可选文本框：
```
能告诉我们哪里不好吗？（可选）
[文本框]              [提交 / 跳过]
```

### 5. **闭环**
用户反馈后，让他知道"被听到了"。
- 简单：弹"感谢反馈"
- 进阶：反馈数据公开（"本月基于反馈改进了 23 个问题"）

## 关键反馈指标

### 👎 率（Thumbs Down Rate）
```
👎 数 / 总反馈数
```
- < 5%：良好
- 5–10%：有改进空间
- > 15%：必须紧急改进

**注意**：分母是"反馈数"，不是"总请求数"（多数用户不反馈）。

### 修正率（Edit Rate）
```
用户编辑 AI 答案的次数 / 总答案数
```
**最强负信号**——用户嫌错到要自己改。

### 重问率（Repetition Rate）
```
用户在短时间内（如 30s）对同一问题改写重问的次数
```
隐式失败信号。

### 拒答率（Refusal Rate）
```
AI 拒绝回答的次数 / 总请求
```
过高 = 系统过度保守，影响体验。

### NPS / CSAT
传统满意度调查，适合定期（不是每次问）。

## 反馈数据怎么用

### 用法 1：发现失败模式
```sql
-- 高 👎 率的 query 模式
SELECT query_pattern, COUNT(*) as n, AVG(rating) as r
FROM feedback
GROUP BY query_pattern
HAVING n > 10
ORDER BY r ASC
LIMIT 20;
```
找出 👎 最集中的 query 类型——这是改进靶子。

### 用法 2：补充 golden set
- 把 👎 的 case 加到离线 golden set
- 下次评估就能测出来
- 这是**离线-在线闭环**的关键

### 用法 3：用户编辑 → 训练数据
用户编辑过的"正确答案"是**最宝贵的训练数据**：
- 微调（如果有量）
- Few-shot 示例
- 评估集

### 用法 4：报警
👎 率突然飙升 → 触发报警 → 立即排查

## 反馈采集的技术实现

### 前端（最小实现）

```html
<div class="ai-response">
  <p id="answer">{{ answer }}</p>
  <div class="feedback">
    <button onclick="feedback({{msg_id}}, 'up')">👍</button>
    <button onclick="feedback({{msg_id}}, 'down')">👎</button>
    <div id="reason-{{msg_id}}" style="display:none">
      <textarea placeholder="能说说哪里不好吗？（可选）"></textarea>
      <button onclick="submitReason({{msg_id}})">提交</button>
    </div>
  </div>
</div>
```

### 后端

```python
@app.post("/feedback")
async def feedback(req: FeedbackRequest):
    # 存到数据库
    db.save({
        "message_id": req.message_id,
        "user_id": req.user_id,
        "rating": req.rating,  # "up" / "down"
        "reason": req.reason,
        "timestamp": now(),
        # 关键：同时记录这条消息的上下文
        "query": req.query,
        "answer": req.answer,
        "context": req.context,    # RAG 召回的文档
        "model": req.model,
        "prompt_version": req.prompt_version,
    })

    # 同步到 Langfuse（如果接了）
    langfuse.score(
        trace_id=req.trace_id,
        name="user-thumbs",
        value=1 if req.rating == "up" else 0,
    )
```

**关键点**：反馈**必须**关联完整的 trace 上下文，否则事后没法分析。

## 反馈偏差（必读）

### 偏差 1：自选偏差
反馈的用户 ≠ 普通用户。
- 极度满意 / 极度不满的人才反馈
- 中间用户沉默

**对策**：
- 关注**绝对数**而不是"率"
- 定期做用户访谈补足"沉默的大多数"

### 偏差 2：暗黑模式偏差
UI 设计影响反馈率：
- 👍👎 放显眼位置 → 反馈率 10%
- 放隐蔽位置 → 反馈率 0.5%
- 但显眼也可能让用户随便点

**对策**：A/B 测位置和形式，找平衡点。

### 偏差 3：用户不知道自己要什么
- 用户说"我要更详细的答案"
- 真的给了详细答案 → 投诉"太长了"
- **用户的反馈 ≠ 用户的真实需求**

**对策**：把用户反馈当**线索**，不当**真理**。配合行为数据看。

## 反馈闭环（最重要的图）

```
在线反馈      ─→   分析失败模式    ─→   改进 prompt/RAG/模型
   ↓                                          ↓
   ↓                                          ↓
补充 golden set ←─  把错例加入评估集 ←─  验证改进效果
   ↓                                          ↓
   ↓                                          ↓
持续监控 ←───────  发布 v2 ←──────────  离线评估通过
```

**没有闭环 = 反馈数据堆在那里发霉**。

## 实战：给 my_com_rag 加反馈系统

### Phase 1（1 天）：最小反馈
- 前端：👍👎 按钮
- 后端：一个 `/feedback` 接口
- 数据：存 SQLite 或文件

### Phase 2（1 周）：闭环
- 把 👎 的 case 加到 golden set
- 写一个 dashboard（哪怕 Notion）：每天 👎 数 / 👎 率 / 主要问题

### Phase 3（2 周）：进阶
- 加用户编辑采集（前端做 inline edit）
- 接入 Langfuse，反馈和 trace 关联
- 设报警：👎 率超阈值 → 飞书/Slack 通知

## 不要做的事

❌ **强制反馈** → 用户糊弄你
❌ **问卷太长** → 没人填
❌ **只看 👎 率** → 漏掉隐式信号
❌ **反馈数据不分析** → 等于没采集
❌ **不闭环到离线评估** → 改进没方向
❌ **隐藏反馈入口** → 等于不采集
