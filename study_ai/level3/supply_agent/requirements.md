# supply_agent 需求定稿

> 2026-11-17 需求访谈记录定稿。业务模式升级：从"工厂供应链管家"改为
> **中间商（贸易商）**——从供应商（A）进货 → 入仓 → 出库 → 卖给客户（B），
> 赚差价。原 Mock 版只覆盖了"买进"半条街，本定稿补齐另一半并埋下扩展键。

## 需求日志（什么时间，提了什么需求——只追加，不删改）

- **2026-11-17**：需求 1~8 一次提出（中间商模式需求访谈）——买手侧：比价、
  供应商质量记录、出货量统计、交付及时率；卖手侧：客户利润最大化、
  月/季/年销售统计；两头：合同条款审查、批次反查合同
- **2026-11-17（续）**：需求 9——角色可组合：可以只当**供应商**（只卖不买）、
  只当**客户**（只买不卖）、或**中间商**（又买又卖）；进货和出货模块
  **可选、可拆分**，不强制绑定

## 业务全景

```
供应商 A ──采购合同──> 采购单 ──收货──> 批次入库（带进价/质检）──> 仓库
                                                              │ 按批次管理（先进先出）
客户 B   <──销售合同── 销售单 <──出库── 批次出库（扣批次余量）<──┘
```

- 库存不是"一个数字"，是**按批次的流水**：入库批次带进价，出库按先进先出扣批次——
  利润、追溯、出货量统计全从流水算出来
- 合同是两头的依据：订单挂合同，批次挂订单——出问题从货反查到合同

## 需求清单（8 条）

| # | 需求 | 侧 | 靠什么数据 |
|---|---|---|---|
| 1 | 同样的货，从哪个供应商拿货便宜（比价） | 买 | 报价表（供应商 × SKU × 单价 × 有效期） |
| 2 | 哪个供应商的产品好（质量记录） | 买 | 批次质检记录（质量是收出来的，不是档案里填的） |
| 3 | 哪个供应商出货量大 | 买 | 采购历史聚合 |
| 4 | 哪个供应商交付及时 | 买 | 订单预计交期 vs 实际收货日 |
| 5 | 卖给哪个客户利润最大化 | 卖 | 卖价 − 批次进价（先进先出成本） |
| 6 | 每月/每季/每年卖给哪个客户最多 | 卖 | 销售历史按时间聚合 |
| 7 | 采购/销售合同条款审查（合不合理） | 两头 | 合同文本 + LLM 审查（检查清单） |
| 8 | 出问题的货 → 追溯到对应合同 | 两头 | 追溯链：合同 → 订单 → 批次 |
| 9 | 角色可组合：只当供应商 / 只当客户 / 中间商；进货、出货可选可拆 | 架构 | 挂载即开关（APP_ROLE 过滤 MCP_CONFIG） |

## 架构决定（访谈中拍板）

1. **MCP 骨架不变**：一域一 Server 一账本 + 工具即合同 + 确认闸门。
   业务加域 = 长新 Server，不推翻现有四座。
2. **数据模型是公共地基**：8 条需求全是"账记得对才查得出"。
   schema 一次设计到位，新域表可空、**关联键必埋**——
   **口诀：宁可表先空着，不可键后补埋。**
3. **成本计价 = 先进先出**：按批次管账天然成立，先买的批次先出库，
   成本自动跟批次走（讨论中已定）。
4. **合同存储 = 双层**：结构化条款表（查得快）+ 原文文件（喂 LLM 审查），
   表里存文件路径。
5. **将要长出的 Server**（按需分阶段，不一次全建）：
   - 销售 Server（客户档案 + 销售单 + 出库写账，与 procurement 对称）
   - 合同 Server（条款存储 + LLM 审查工具）
   - 报表 Server（只读聚合：比价 / 供应商考评 / 客户统计 / 利润）
6. **挂载即开关**（需求 9 的机关，站 2 落地）：`APP_ROLE` 环境变量定角色——
   `trader`（默认，四座全挂）/ `buyer`（只挂 supplier+procurement 买手侧）/
   `seller`（只挂 customer+sales 卖手侧，库存靠期初批次）。agent.py 按角色
   过滤 MCP_CONFIG + 调整 system prompt——**只改配置不改代码**（与站 6
   的 APP_ENV 同一哲学）。数据层天然支持：采购/销售本就是两张独立表，
   流水带方向字段，单方向流水合法。
